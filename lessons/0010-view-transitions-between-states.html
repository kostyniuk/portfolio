Animate Between Page States

Skill: recognize when a change is too structural for transitions or keyframes, and hand it to the browser's snapshot machinery instead.

The Problem This Solves

Every primitive so far animates an element's own properties. But the hardest UI changes aren't property changes — they're structural: a grid reorders when a filter is applied, a card moves to a different slot, the page navigates. Transitions and keyframes are nearly useless here, for a deep reason: when React re-renders or the layout reflows, the "moved" element may be unmounted and remounted, and its position is decided by layout, not by an animatable property. There is no translate to transition.

The pre-existing answer was the FLIP technique: in JavaScript, measure every element's position, apply the change, measure again, then fake the motion with inverted transforms. It works, and it's exactly the kind of fiddly measurement code people wanted gone. The desire behind the View Transition API: "I'll change the DOM however I like — browser, you figure out how to morph the old screen into the new one."

The Idea: Animate Snapshots, Not Elements

A view transition is not an element animation. When you call document.startViewTransition(update), the browser photographs the page, runs your update function (any DOM change at all), photographs the result, and cross-fades between the two photos. Give an element a view-transition-name and it's paired across the snapshots — the browser computes the position and size delta and morphs it from old slot to new, doing FLIP's job natively.

The snapshots are real pseudo-elements (::view-transition-old(...), ::view-transition-new(...)), so you style the transition with ordinary CSS — the demo below just sets animation-duration on them.

document.startViewTransition(() => {
  scene.classList.toggle("alternate");

/* the featured tile is paired across snapshots */
.featured { view-transition-name: featured-tile; }
::view-transition-old(featured-tile),
::view-transition-new(featured-tile) { animation-duration: 420ms; }

Notice the update itself is one class toggle. The entire morph — the tile gliding to its new slot, the other tiles cross-fading — comes from the browser diffing the snapshots.

The Trade-Off

Snapshots are photos, not live elements: while the transition runs, the page isn't interactive and content inside the snapshots is frozen. So this is the wrong tool for continuous or interactive motion (hover effects, scroll reveals) and the right tool for discrete moments — a filter applied, an item promoted, a route change. The other primitives keep elements alive; this one trades liveness for the ability to animate any change. Always keep the no-support fallback in the demo's shape: run the update directly, so the change still happens without the morph.

On Your Portfolio

Two natural fits: reordering or filtering the project grid (the demo above is exactly that, with view-transition-name on each card), and page navigation — Next.js can drive same-document view transitions on route change, giving the portfolio app-like page-to-page morphs. Both are "discrete moment" changes, squarely in this primitive's territory.
