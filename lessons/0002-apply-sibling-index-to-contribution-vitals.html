Apply The Stagger To Real Markup

The useful move in the contribution vitals was not just adding an animation. It was making every animated item a direct sibling so sibling-index() can count the sequence correctly.

The Problem This Solves

Lesson 1 worked on an idealized flat list. Real component markup is almost never flat: wrappers accumulate for styling, layout, and component boundaries — a .stats div here, a .repos div there. That's harmless until you reach for sibling-index(), because it counts within one parent only. Nested groups each restart the count at 1, so two items in different wrappers get the same index and animate at the same time, and the "sequence" quietly becomes two overlapping sequences.

So the real skill isn't writing the delay formula — it's reading markup as the data structure CSS will count, and reshaping it so that source order is animation order. This is a general lesson about modern CSS: features like sibling-index() derive everything from document structure, which means the structure itself becomes part of the animation design.

Before: Nested Groups Interrupt The Count

If stats live inside one wrapper and repos live in another, each group gets its own sibling order. That makes the timing harder to reason about.

<div class="vitals">
  <div class="stats">
    <Stat />
    <Stat />
  </div>

  <div class="repos">...</div>
</div>

After: Direct Animated Siblings

Give each animated block the same class and place them under the same parent. Now the source order is the animation order.

<div class="contribution-vitals-stagger">
  <Stat />
  <Stat />
  <Stat />
  <Stat />
  <div class="contribution-vital">Repos</div>
</div>

The CSS Pattern

.contribution-vitals-stagger {
  view-timeline: --contribution-vitals block;
}

.contribution-vitals-stagger > .contribution-vital {
  --i: calc(sibling-index() - 1);
  --enter-x: 0;
  --enter-y: 1rem;
  animation: contribution-vital-in linear both;
  animation-timeline: --contribution-vitals;
  animation-range: cover 0% cover 20%;
}

.contribution-vital:nth-child(1) { --enter-x: -2rem; }
.contribution-vital:nth-child(2) { --enter-y: -1.35rem; }
.contribution-vital:nth-child(5) { --enter-x: 2rem; }

This mirrors the page reveal pattern: every item uses the same cover 0% cover 20% timeline window. Use sibling-index() for per-item choices like direction or intensity, not necessarily for shifting the timeline itself.

The boundary to respect: flattening has a cost. The wrappers you remove were doing layout work, so the flat parent must take it over (here, one flex container handles all five items). If flattening would wreck the layout or the component structure, that's the signal to fall back to a JS-provided index rather than contort the markup to make CSS counting possible.

Practice Check

Question: why did we put the repo block directly inside .contribution-vitals-stagger instead of leaving it in a separate wrapper?

On Your Portfolio

This is the change live in features/contributions/vitals.tsx: the stat blocks and the repos block share one parent with one class, and the timing rules live entirely in CSS. The payoff of the flat shape is durability — reorder the stats in JSX and the animation order follows automatically; add a sixth vital and it joins the stagger with zero CSS changes.
