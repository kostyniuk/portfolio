Scroll Can Be The Timeline

Skill: link animation progress to scroll position instead of time.

The Problem This Solves

Scroll-linked effects — reading progress bars, parallax, reveal-on-scroll — used to be a JavaScript tax. You attached a scroll listener, recalculated positions on every event, throttled it so it wouldn't melt the main thread, and still got jank: scrolling happens on the browser's compositor thread, but your JavaScript ran on the main thread, so the effect always lagged a frame or two behind the actual scroll. IntersectionObserver helped with "did it enter the viewport?" but gives discrete events, not continuous progress — useless for a progress bar.

The underlying desire was simple: "this animation's progress should just be the scroll position." Scroll-driven animations grant exactly that, declaratively, with the browser doing the math off the main thread.

The Idea: Swap The Clock

Recall from lesson 5: keyframes are a timeline, and something moves the progress along it. By default that something is the clock. animation-timeline replaces the clock with a scroller:

Time-based animation says: "after 500ms, be halfway done." Scroll-driven animation says: "when scroll is halfway, be halfway done."

Everything else carries over unchanged — same @keyframes, same easing concepts. Duration becomes meaningless (scroll distance replaces it), and you get two properties for free that JavaScript versions had to hand-build: the animation is perfectly reversible (scroll up and it rewinds, watch the bar) and perfectly synchronized (it can never lag the scroll, because scroll position is the input).

Page Progress Demo

Scroll this lesson. The sticky bar at the top is not timed; it is driven by root scroll progress.

.bar::before {
  animation: fill linear both;
  animation-timeline: scroll(root block);
}

Two Kinds Of Scroll Timeline

scroll() measures how far a container has scrolled — right for whole-page effects like this progress bar. view() measures how far a specific element has traveled through the visible area — right for per-element reveals, and the subject of the next lesson. Choosing between them is the first question for any scroll effect: is the driver the page, or the element?

One honest caveat: linear easing is usually correct here. The user's finger provides the easing — adding a curve on top makes the element feel detached from the scroll.

On Your Portfolio

Your main page's viewport reveal is already a view() timeline animation. Understanding that scroll is "just another clock" means every keyframe trick you know — staggering with sibling-index(), holds, multi-beat sequences — can be driven by scroll with a one-line change.
