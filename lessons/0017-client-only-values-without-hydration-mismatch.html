The Server Has No Clock

Skill: render a value that only exists in the visitor's browser — their local time, timezone, viewport, or stored preference — without triggering a React hydration mismatch or starting an entrance animation with placeholder content.

The problem it solves

You want the hero to greet visitors with “Good morning”, “Good afternoon”, “Good evening”, or “Good night” depending on the time of day. The obvious move is to call new Date() in the component and branch on the hour.

The exact failure depends on where that code runs. A pure React Server Component runs on the server and is not re-run in the browser during hydration, so it can ship server time without a hydration mismatch. That is still wrong for a visitor-local greeting: the browser never gets a chance to correct it unless you introduce a Client Component.

A Client Component has the sharper trap. Next.js renders it once on the server to produce HTML, then the browser downloads React and hydrates it by running the component again on the client. Hydration is an assertion: “the first client render equals the server render.”

A clock can break either goal:

  • Different machines. In an RSC or server pre-render, new Date() reads the server's wall-clock and timezone (often UTC, in some datacenter). The visitor in Kyiv could be six hours off. The server literally cannot know the visitor's local time.
  • Different renders. In a Client Component, the server render might produce one greeting, while the first browser render reads the visitor's clock and produces another. Then the hydration assertion fails.

When a Client Component's texts disagree, React logs Hydration failed because the server rendered HTML didn't match the client, throws away the server markup for that subtree, and re-renders it on the client. Before React 19 that could silently corrupt the DOM; today it is a loud error. Either way the thing you wanted — fast, correct first paint — is gone.

The idea: render twice on purpose

The fix is to stop pretending the server knows. Split rendering into two passes:

Pass 1 — the agreed render. Produce a value the server and the first client render can both compute identically: a neutral placeholder, or a deterministic default. Hydration compares this render to the server HTML, so they match and React stays happy.

Pass 2 — the truth. useEffect runs only in the browser, only after hydration has already succeeded. There you read the real client-only value and setState. React re-renders — now safely, on the client alone — and the correct text appears.

The mental model: hydration is a handshake, not a render. You must show the server's answer first so the handshake completes, then quietly swap in the browser's answer once you're allowed to disagree.

You have already shipped this exact pattern. usePrefersReducedMotion in this repo defaults to false (the agreed render), then reads matchMedia in an effect (the truth). prefers-reduced-motion is a client-only value for the same reason the clock is — the server can't read the visitor's OS setting.

The hook, in its clearest form

The two-pass idea is easiest to read written by hand — this is exactly the shape of your existing usePrefersReducedMotion:

// The mental-model version — same shape as usePrefersReducedMotion
export function useDayTime(): DayTime | null {
  const [dayTime, setDayTime] = useState<DayTime | null>(null); // pass 1: agreed render

  useEffect(() => {
    setDayTime(getDayTime(new Date())); // pass 2: the truth, browser-only, after hydration
  }, []);

  return dayTime;
}

null is the agreed render — the one value the server and the first client render share. new Date() lives inside useEffect, which never runs on the server and never runs during the hydration render, so the only code that touches the clock is the only code allowed to disagree with the server. And because the effect runs in the browser, getHours() reads the visitor's timezone for free — no timezone library, no header parsing.

The hook, as this repo actually ships it

Reading a browser value into state inside an effect is common enough that React built a primitive for it: useSyncExternalStore. It takes the two passes as explicit arguments — a server snapshot and a client snapshot — so React, not your effect, owns the swap. This repo's newer react-hooks lint rule (set-state-in-effect) flags the hand-written form, which is the nudge toward this one:

"use client";

import { useSyncExternalStore } from "react";

export type DayTime = "morning" | "afternoon" | "evening" | "night";

function getDayTime(date: Date): DayTime {
  const hour = date.getHours();
  if (hour < 5) return "night";
  if (hour < 12) return "morning";
  if (hour < 18) return "afternoon";
  if (hour < 22) return "evening";
  return "night";
}

const subscribe = () => () => {};            // we read once, never subscribe
const getServerSnapshot = (): DayTime | null => null; // pass 1: the agreed render

export function useDayTime(): DayTime | null {
  return useSyncExternalStore(
    subscribe,
    () => getDayTime(new Date()),            // pass 2: the truth, client only
    getServerSnapshot,
  );
}
"use client"

Hooks only run in Client Components. This directive marks the module's exports as the client boundary. The Server Component page stays a server component; it just renders a client child.

getServerSnapshot => null

This is the agreed render, named outright. React uses it on the server and on the first hydration render, so both sides produce null and the handshake passes. Picking a real default like "morning" would be a guess that is often wrong.

() => getDayTime(new Date())

The client snapshot. React calls it in the browser after hydration and swaps the result in safely. It returns a primitive string, so React's Object.is check stays stable between calls and never loops.

subscribe is a no-op

We only want the value once, at mount — we are not tracking the clock minute by minute. The empty subscribe means React reads the snapshot once and never re-runs. (If you wanted a live ticking greeting, this is where a timer subscription would go.)

Both versions are the same two-pass pattern. The hand-written one shows the mechanism; useSyncExternalStore is the primitive React built for exactly this, and the one to reach for when the lint rule (rightly) objects to reading a browser value into state inside an effect.

Wiring it into the hero

The page stays a Server Component. A thin client component owns the dynamic text and hands it to the existing animated headline. The important detail is that the animated component does not mount until the clock has resolved:

"use client";

import { LovableAnimatedText } from "./lovable-animated-text";
import { useDayTime } from "./use-day-time";

export function LovableGreeting({ className }: { className: string }) {
  const dayTime = useDayTime();

  // null on the server and first client render -> invisible placeholder
  // on both sides. Hydration succeeds, and no reveal animation has started.
  if (!dayTime) {
    return (
      <h2 className={className} aria-hidden="true" style={{ perspective: 1200 }}>
        <span className="invisible flex flex-wrap items-baseline justify-center gap-x-[0.28em] gap-y-2 text-white/85">
          Good afternoon Lovable team, I&apos;m Alex
        </span>
      </h2>
    );
  }

  const text = `Good ${dayTime} Lovable team, I'm Alex`;

  return <LovableAnimatedText className={className} text={text} />;
}

Server and first client render both produce the same hidden placeholder. Hydration passes. Then the snapshot resolves, LovableAnimatedText mounts for the first time, and the line reveals as “Good morning Lovable team, I'm Alex”.

The animation bug hiding inside the hydration fix

The two-pass pattern solves the React error, but it does not automatically solve the animation. Your first version used a visible fallback:

const text = `Good ${dayTime ?? "day"} Lovable team, I'm Alex`;

That is hydration-safe: server and first client render both say “Good day”. But the headline reveal starts immediately with the fallback word. A moment later dayTime resolves and “day” becomes “morning”, which means the visitor sees a text correction in the middle of a carefully timed entrance.

The first repair was to stop remounting animated wrappers on text changes:

// Better identity for a fixed sentence: the second slot stays the second slot.
{words.map((word, index) => (
  <RotateAppearance key={index} delayMs={startDelayMs + index * staggerMs}>
    {word}
  </RotateAppearance>
))}

That prevents the reveal from replaying when the word changes, but it still allows the word to change during the reveal. The final repair is the gate above: reserve layout with invisible content, then mount the animated text only once the client-only value is real.

The useful distinction is: hydration correctness is about markup equality; animation correctness is about lifecycle timing. You often need both.

For a hero whose entrance animation is the whole point, gating the reveal is the cleanest version. The user does not see a wrong word, React does not see mismatched markup, and the animation does not have to pretend a placeholder was real content.

Boundaries — when two-pass is the wrong tool

  • When server time is acceptable, keep it in an RSC. There is no hydration mismatch because the browser does not re-run that Server Component. But it is server-local time, not visitor-local time.
  • When you can know the visitor value on the server, do that instead. If you only need the timezone (not the exact instant), you can read a hint server-side and skip the swap entirely — no flash, correct first paint. That is a different technique; ask about reading request headers or a cookie.
  • When the value is a media query or device capability, reach for the same shape as usePrefersReducedMotion rather than writing a clock-specific hook each time.
  • When CSS can do it without knowing the value at all, prefer CSS. A purely decorative time-of-day tint could be a media feature; a greeting word is real content, so it needs the hook. This is the same CSS-vs-React ownership split from the Motion lesson.
  • Never reach for typeof window !== "undefined" inside render to branch. It produces exactly the mismatch you're trying to avoid — the server takes one branch, the client's first render takes the other. The branch belongs in an effect, not in render.

Mission tie-in

This is the first lesson in your workspace about a value that lives only in the browser and must survive the server→hydrate round trip — the substrate every interactive animation in this portfolio sits on. The Lovable hero is the concrete target: it turns a static greeting into a time-aware reveal while staying a Server Component, reusing the exact two-pass shape your usePrefersReducedMotion hook already proves out. Once this pattern is reflexive, “does this depend on something only the browser knows, and will it disturb an animation if it changes later?” becomes the first question you ask before any client effect.
