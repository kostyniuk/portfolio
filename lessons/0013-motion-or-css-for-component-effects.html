Motion or CSS?

Skill: decide whether a reusable React animation component belongs in plain CSS or in Motion before writing the component.

The problem it solves

CSS is excellent when the browser already knows the trigger: hover, focus, a class change, a scroll timeline, or a named keyframe loop. The trouble starts when the animation depends on React state, keyed children, measured layout, or elements that are about to leave the tree.

Without a decision rule, animated components drift into an awkward middle: CSS handles some timing, JavaScript timers handle other timing, refs measure widths, and exit states are patched in later. The component works, but nobody can tell which layer owns the effect.

The idea

Use CSS when the stylesheet can answer the whole question. Use Motion when the component needs React information to describe animation state. Motion's React docs describe motion elements as standard elements extended with animation props, and AnimatePresence exists specifically for exit animations when elements are removed from the React tree.

A helpful way to phrase it: CSS is great at reacting to the document; Motion is great at reacting to the component. CSS can see selectors, pseudo-classes, media queries, and scroll timelines. React can see props, state, keys, timers, refs, and whether a child is being mounted or removed. Motion sits in that React layer and turns those values into animation instructions.

The decision flow

1 Can CSS observe the trigger?

If the trigger is :hover, [data-state=open], @media, a class, or scroll position, start with CSS. If the trigger is React state, a prop, a key change, or a timer inside the component, keep reading.

2 Does anything need to exit after React removes it?

If yes, CSS alone is fighting React. Once React removes a node, CSS cannot animate it. Use Motion's AnimatePresence so the exiting element remains present until its exit animation finishes.

3 Does the target value come from runtime measurement?

If the animation target depends on offsetWidth, a ref, a computed layout value, or arbitrary prop data, React is already involved. Motion or React plus CSS is usually clearer than pretending the stylesheet knows those values.

4 Is the visual texture independent of React?

If the effect is just a repeating shimmer, pulse, gradient sweep, or transform loop, keep that part in CSS even inside a Motion component. Let React trigger it; do not make React draw it.

Question Plain CSS is enough when... Reach for Motion when...
What starts it? A selector, media query, class, scroll timeline, or keyframe clock. React state, keyed children, route state, gesture state, or conditional rendering.
What must be known? The start and end styles are static or selector-derived. The effect needs measured width, dynamic variants, or values computed from props.
What is leaving? Nothing leaves, or hiding with CSS is acceptable. A React child is unmounted but still needs an exit animation.
Reduced motion? @media (prefers-reduced-motion: reduce) can swap or remove the animation. A component must branch at runtime with useReducedMotion().

Practice

Classify each effect. The feedback explains the ownership boundary.

Effect: a button lifts by 2px on hover.

Effect: a rotating headline word exits upward before the next word enters.

Effect: an underline sends one gradient shimmer across a fixed-width word.

Effect: a word slot smoothly resizes to whatever string React renders next.

Code shape

The split headline component follows the rule: CSS owns the reusable shimmer keyframe; Motion owns the React-aware reveal and keyed word swap.

export function AnimatedHeadline(props) {
  return (
    <motion.h2 style={{ perspective: 1200 }}>
      <RotateAppearance>Frontier</RotateAppearance>
      <RotateWord words={["build", "create"]} />
    </motion.h2>
  );
}

How this maps to the headline

Effect Why not just CSS? Chosen owner
Word-by-word flip-up reveal CSS can do the visual reveal, but the composed React component already calculates delay from props. RotateAppearance uses Motion with a delayMs prop.
Rotating word swap The word list, timer, key changes, exit animation, and measured width all live in React. RotateWord uses React state, refs, and Motion presence.
Shiny underline sweep CSS can fully draw the gradient and move its background position. ShinyUnderline keeps the shimmer keyframe in CSS; React only replays it with a key.

Boundaries

  • Do not use Motion because a thing moves. Use it because React owns information CSS cannot see cleanly.
  • Do not force CSS to simulate unmounting. CSS cannot animate a node after React has removed it; Motion's AnimatePresence keeps it around for the exit animation.
  • Do not put every visual detail into Motion props. Static repeated effects like a shimmer keyframe remain clearer in CSS.
  • Reduced motion is not optional polish. CSS has prefers-reduced-motion; Motion has useReducedMotion(). Pick the one that matches where the effect lives.

Mission tie-in

Your portfolio now has animated UI primitives that are not purely CSS primitives. The mission becomes sharper: keep simple animation in CSS, but when a component's state, measurement, or lifecycle owns the animation, use Motion deliberately and leave a CSS comparison in the lesson.
