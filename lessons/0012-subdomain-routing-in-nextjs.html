Subdomain Routing in Next.js

Today you wanted https://www.lovable.a13x.space/ to render the existing /lovable page. The skill is learning which part belongs to DNS, which part belongs to Vercel, and which part belongs to Next.js.

The problem it solves

A path route is easy: /lovable maps to app/lovable/page.tsx. A subdomain is different. The browser first has to find a server for www.lovable.a13x.space, and only after that can your Next app decide what page to render.

Without separating those layers, it is easy to edit app code while DNS still points nowhere, or to add DNS while the app still renders the normal homepage.

The idea

1

DNS turns a hostname into a destination. For Vercel subdomains, that is usually a CNAME record.

2

Vercel domains decide which project is allowed to receive that hostname and provision HTTPS for it.

3

Next rewrites inspect the Host header and serve an internal route while keeping the visible URL.

That third step is what we changed in next.config.mjs. Next.js documents rewrites as a way to map one incoming path to another destination path while masking the destination URL, and its rewrite matching supports has rules for host values.

What DNS is doing

DNS is the internet's lookup system for names. Humans type names like www.lovable.a13x.space; browsers need to know where to send the request. DNS records are the small pieces of data that answer that lookup.

Piece Plain-language meaning In this setup
a13x.space The domain, also called the zone when you are editing its DNS records. Your zone is managed by Vercel nameservers.
www.lovable The record name inside the a13x.space zone. Vercel combines it into www.lovable.a13x.space.
CNAME An alias from one hostname to another hostname. The subdomain aliases to Vercel's domain-specific target.
A A direct mapping from a hostname to an IPv4 address. Useful for apex domains like a13x.space, not the subdomain we added.
TTL How long DNS resolvers can cache the answer. 60 means changes can be checked again quickly, though caches can still take time.

Why the first attempt failed: the form was set to A, so Vercel expected an IPv4 address in the value field. The target Vercel showed you was a hostname, so the correct type was CNAME.

Why Vercel needs its own domain entry

The DNS record says, "send this hostname to Vercel." The project domain entry says, "this specific Vercel project is allowed to answer for this hostname." That second step matters because Vercel hosts many projects. It also lets Vercel provision the HTTPS certificate for the exact hostname.

That is why we saw the domain begin resolving to Vercel, but HTTPS still failed before the project domain was fully configured: the request could reach Vercel, but Vercel had not finished treating www.lovable.a13x.space as a valid secure hostname for this project.

What we changed

async rewrites() {
  return {
    beforeFiles: [
      {
        source: "/",
        has: [
          {
            type: "host",
            value: "www\\.lovable\\.a13x\\.space(?::\\d+)?",
          },
        ],
        destination: "/lovable",
      },
    ],
  };
}
source: "/"

Only the root of the subdomain is rewritten. Assets and other paths keep working normally.

type: "host"

The rule only runs when the request host is www.lovable.a13x.space.

destination: "/lovable"

Next renders the existing Lovable route without redirecting the browser.

beforeFiles

The homepage at / already exists, so the host-specific rewrite must run before filesystem page matching.

What Vercel asked for

After adding www.lovable.a13x.space to the portfolio project's Domains page, Vercel recommended a DNS change like this:

Field Value we used Why
Type CNAME Subdomains can point at another hostname.
Name www.lovable You were editing the a13x.space zone, so the form only needed the prefix.
Value 8034576ba7dae91d.vercel-dns-017.com. Vercel's current recommended domain-specific target for this project/domain.
TTL 60 A short cache time while the setup settles.

The final dot in the CNAME value matters when Vercel shows one. It means the value is a full absolute hostname, not something that should be completed with a13x.space after it.

Practice

Use this mental debugger: when a subdomain fails, ask which layer is failing.

Scenario: www.lovable.a13x.space shows a browser DNS error before any request reaches Vercel. Which layer should you inspect first?

Scenario: Vercel's DNS form says value should match format "ipv4". What does that tell you?

Local test command:

curl -H "Host: www.lovable.a13x.space:3000" http://127.0.0.1:3000/

This works because the Host header is the same signal Vercel will pass to Next in production.

Boundaries

  • A rewrite does not create DNS records. You still have to add the subdomain to Vercel and point DNS at it.
  • A rewrite is not a redirect. The browser URL stays / on the subdomain, while the app internally renders /lovable.
  • A broad rewrite like /:path* can accidentally catch images and framework assets. For this case, exact / is safer.
  • If you wanted many tenant subdomains, you would likely move this into a more general host-routing layer instead of hard-coding one hostname.

How we made it work on Vercel

  1. Created the page: the Lovable background lived at app/lovable/page.tsx and used public/lovable/pulse.webp.
  2. Added a host rewrite: next.config.mjs maps www.lovable.a13x.space/ to the internal /lovable route.
  3. Added the domain to the project: in Vercel, Project Settings -> Domains, we added www.lovable.a13x.space.
  4. Read Vercel's recommended DNS record: Vercel asked for a CNAME named www.lovable pointing at 8034576ba7dae91d.vercel-dns-017.com..
  5. Added the DNS record in the a13x.space zone: because the domain uses Vercel nameservers, the DNS record was added in Vercel's domain DNS UI.
  6. Waited for validation: after DNS updated, Vercel could verify the domain and issue HTTPS.
  7. Opened the final URL: https://www.lovable.a13x.space/ now reaches Vercel, passes the host to Next.js, and renders the Lovable route.
