Choose The Animation Primitive

Skill: decide whether a motion belongs to a transition, a time-based animation, or a scroll-driven animation — before writing any code.

The Problem This Solves

CSS used to have exactly one animation story: write some @keyframes or a transition, and reach for JavaScript for everything else. That left whole categories of motion — scroll effects, entry animations, layout morphs — stuck in JS, with scroll listeners, requestAnimationFrame loops, and libraries to maintain.

Today CSS has four distinct primitives, and most animation frustration comes from picking the wrong one: writing keyframes to fake a hover effect, wiring up JavaScript scroll handlers to do what animation-timeline: view() does for free, or hand-animating a layout change the View Transition API would handle in three lines. Choosing the right primitive first is the highest-leverage skill in this whole series.

The Idea: Ask "What Drives The Progress?"

Every animation is a value going from 0% to 100%. The primitives differ in what moves that progress along:

Transition — progress is driven by a state change. Something flipped (hover, focus, a class toggle), and the browser smooths the gap between old and new style. You only describe the two end states.

Keyframes — progress is driven by the clock. You choreograph beats at percentages, and the animation plays through time, optionally looping. Nothing has to "change" to start it.

Scroll-driven animation — progress is driven by the scrollbar. Same keyframes syntax, but scroll position replaces the clock. Scrolling back rewinds it; no JavaScript listens to anything.

View transition — progress is driven between two document snapshots. The browser photographs the page before and after a DOM change and morphs between the photos. This is for changes too structural for the other three (reordering, navigation).

Why This Matters For Your Portfolio

Your portfolio already mixes three of these: the viewport reveal on the main page is a scroll-driven animation with a fixed range, hover lifts on cards are transitions, and the staggered contribution vitals from lesson 2 are keyframes with sibling-index() delays. Naming which primitive each effect uses is what lets you extend them without adding JavaScript — which is exactly the mission.
