Dual Triggers —
Independent Entry and Exit Speeds

Skill: define two named timeline-triggers on one element to give entry and exit animations different durations — without any JavaScript.

The Problem This Solves

Once you wire animation-trigger: --t play-backwards, the reverse plays at the same duration as the forward. A slow, satisfying draw-on (1.4 s) followed by a 1.4 s slow erase feels sluggish on the way out.

The common JS workaround is to conditionally unmount the element — which makes the exit instant (abrupt), not fast. You trade slow for jarring, plus you pay the cost of useState, an IntersectionObserver, and "use client".

The real goal: slow draw-in, fast fade-out, zero JavaScript.

The Idea: Two Names, Two Ranges

A timeline-trigger is a named trigger derived from an element's view progress. One element can carry multiple named triggers, each covering a different slice of its viewport journey:

.section {
  timeline-trigger:
    --hints     view() entry 50% exit 50%,   /* active while section is "on screen" */
    --hints-out view() exit 20% exit 100%;   /* active only while leaving            */
}

Read the range as two waypoints: activate at this point, deactivate at that point. entry 50% means "halfway through the entering phase"; exit 20% means "20 % into the exiting phase". Each animation subscribes to whichever trigger name controls it:

/* Slow draw — plays in on --hints, reverses (invisibly) on --hints deactivation */
.path {
  stroke-dasharray: 1500;
  animation: draw 1.4s cubic-bezier(.65,0,.35,1) both;
  animation-trigger: --hints play-forwards play-backwards;
}

/* Fast exit — fades the whole overlay out the moment --hints-out activates */
.overlay {
  animation: fade-out 0.25s ease both;
  animation-trigger: --hints-out play-forwards play-backwards;
}
@keyframes fade-out {
  from { opacity: 1; }
  to   { opacity: 0; }
}

Why Two Animations Can Coexist: Different Properties

This is the crux of the technique. When the section exits:

  • --hints deactivates → draw plays backwards on stroke-dashoffset (1.4 s)
  • --hints-out activates → fade-out plays forwards on opacity (0.25 s)

Because they animate completely different CSS properties, there is no conflict. Both run simultaneously with no precedence fight. The 0.25 s opacity fade is what the user sees; the 1.4 s draw-reversal runs silently underneath an already-transparent overlay.

Contrast this with the case where you need the draw itself to erase faster — that would require two animations both competing for stroke-dashoffset. In CSS, when multiple animations target the same property, the last one in the animation list wins. You can exploit that ordering deliberately, but it's significantly more fragile: you have to sequence them so the erase animation is declared last, and manage what happens to both fill states on re-entry. The different-property approach sidesteps that entirely.

/* Entry animates stroke-dashoffset (the draw) */
/* Exit animates opacity (the fade)             */
/* → no property conflict, no ordering tricks needed */

On re-entry: --hints-out deactivates → fade-out plays backwards (opacity 0 → 1, 0.25 s). --hints activates → draw plays forwards again (stroke-dashoffset 1500 → 0, 1.4 s). The overlay is visible again just as the paths start drawing.

Why fixed children still inherit the trigger

In the real portfolio the overlay is position: fixed, which breaks it out of the layout flow — but not out of the DOM tree. CSS cascade (including named triggers) is DOM-based, not layout-based. A fixed child still inherits --hints and --hints-out from its ancestor section, for the same reason CSS custom properties work inside portals and fixed dialogs.

This means the section element can stay as the single point of truth for scroll detection, even though the animated overlay appears to cover the whole viewport.

No JavaScript Required

The final component is a plain server component — no "use client", no useState, no IntersectionObserver, no timer cleanup. The scroll-awareness, entry animation, and fast exit are entirely owned by CSS. React renders static HTML; the browser does the rest.

// Before: 50+ lines with hooks, IntersectionObserver, animKey state
// After: pure server component, no hooks at all
export function LovableHintsSection() {
  return (
    <section className="lovable-hints-trigger ...">
      <div className="lovable-hints-overlay pointer-events-none fixed inset-0 z-50">
        <svg>...paths...</svg>
        <div className="lovable-header-hint-label ...">Click to open Portfolio</div>
        <div className="lovable-header-hint-label ...">Click to Download CV</div>
      </div>
    </section>
  );
}

Boundaries: When This Doesn't Fit

Browser support: animation-trigger is Chrome 130+ only at time of writing. Firefox and Safari don't support it yet. Appropriate for a portfolio or demo page; not yet for production with broad browser reach. Verify at caniuse.com.

True per-direction duration: play-backwards always uses the same animation-duration. The overlay-fade trick covers the exit visually — but if you need the draw itself to erase at a different speed, you need a second keyframe animation (erase) on a second trigger, ordered last in the animation list so it wins the property conflict. That's a more complex setup.

When to stay on IntersectionObserver: if the exit requires different content — conditional rendering, data fetching, state changes — that belongs to the component layer. animation-trigger is purely for CSS-controlled visual timing.

On Your Portfolio

This is exactly the pattern powering the header hints section on the Lovable page (app/lovable/lovable-header-hints.tsx). The section carries two triggers in globals.css: --hints for the full on-screen range, --hints-out for the exit-only range. The overlay wrapper carries the fast fade; the SVG paths carry the slow draw. Visiting the section draws the arrows; scrolling away fades them in 0.25 s.

The prior version used useState + IntersectionObserver to mount/unmount the overlay — which gave correct scroll-awareness but an abrupt exit. This pattern replaced all of that with two CSS properties and a 10-line keyframe.
